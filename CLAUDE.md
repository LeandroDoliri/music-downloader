# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Desktop app (Windows-focused) for downloading audio/video from YouTube and Spotify. A pywebview window hosts a plain HTML/CSS/JS frontend (`web/`); the Python backend (`main.py`) builds command lines and runs `yt-dlp` and `spotdl` as subprocesses. User-facing strings and code comments are in Spanish — keep new UI text in Spanish.

## Commands

```bash
pip install -r requirements.txt   # pywebview, yt-dlp, spotdl
python main.py                    # run with a console (see Python errors)
pythonw main.py                   # run without a console (how end users launch it; "Music Downloader.lnk")
```

External programs: `ffmpeg` must be on PATH (conversion/merging), and `deno` should be (yt-dlp needs a JS runtime to see all YouTube formats). There are no tests, linter, or build step. The frontend has no bundler — edit `web/*` and relaunch.

The command builders are pure functions, so CLI changes can be checked without the GUI: `python -c "import main; print(main.build_ytdlp_command({...}))"`, or drive `main.Api()` with a fake window object that records `evaluate_js` calls and verify outputs with `ffprobe`.

`icon.ico` (all Windows sizes, 16–256 px) and `icon.png` are generated by `python tools/make_icon.py` (needs Pillow). Edit the script instead of the images. The header logo in `web/index.html` is an SVG of the same glyph, so keep the two in sync.

**Installer:** `tools/build_installer.ps1 [-Version x.y.z] [-Clean]` builds `dist\MusicDownloaderSetup-<version>.exe` (needs Inno Setup 6) and `dist\MusicDownloader-update-<version>.zip` (see Self-update). The version defaults to the `VERSION` file. It stages `build\stage` with the official embeddable Python (with `import site` enabled in its `._pth`, pip, and `requirements.txt` installed using `--no-build-isolation`, because the `._pth` hides pip's isolated build env and `proxy_tools` is sdist-only), `bin\` with ffmpeg/ffprobe/deno, and the app files (plus `VERSION`, `RUNTIME` and `requirements.txt`). Shortcuts point at `python\pythonw.exe "main.py"` with `icon.ico`. There is deliberately no custom launcher `.exe`: Windows 11 Smart App Control blocks unsigned executables, while `pythonw.exe` (PSF) and `deno.exe` are signed and ffmpeg has reputation. For the same reason, the Inno Setup installer itself (its unsigned `setup.tmp`) fails with exit code 1 on PCs where Smart App Control is on, including the dev machine. There, `tools/install_local.ps1` (`build_installer.ps1 -NoSetup` stages without ISCC) installs `build\stage` to the same folder, creates the shortcuts with WScript.Shell, registers an HKCU uninstall entry and copies itself as `uninstall.ps1` (`-Uninstall`). The only real fix for Setup is code signing. `installer/MusicDownloader.iss` installs per-user into `%LOCALAPPDATA%\Programs\Music Downloader` with no admin rights, so `update_tools()` can still pip-upgrade inside the install. `main.py` prepends its sibling `bin\` to `PATH` when it exists. Shortcuts carry the same AppUserModelID as `main.py`. Downloads are cached in `build\downloads`.

To iterate on the UI without pywebview, `.claude/launch.json` defines a `web-ui` config that serves `web/` on `http://localhost:8765`. `window.pywebview` doesn't exist there, so stub `window.pywebview.api` (including `check_environment`), dispatch `pywebviewready`, and call `appendLog` / `onDownloadComplete` by hand to exercise the states. The UI follows the OS light/dark theme via `prefers-color-scheme`; check both. Layout: from 860 px wide (the window opens at 1000×760), `.layout` is two columns, with download on the left (`.col-main`, where status/log fill the leftover height) and advanced options always open on the right (`.col-options`, the accordion becomes a fixed panel). Below that width both columns are `display: contents` and `order` stacks everything in the original single-column order (options between folder and the download button). Check both widths.

## Architecture

**JS → Python:** `main.py`'s `Api` instance is passed as `js_api`, so its public methods are callable from JS as `window.pywebview.api.<method>()` (returns a Promise). Exposed methods: `choose_directory()`, `download(tool, options)` (returns `False` if busy), `cancel()`, `check_environment()`, `update_tools()`, `check_app_update()`, `apply_app_update()` and `open_release_page()`, plus the account methods. Methods prefixed with `_` are not exposed.

**Python → JS:** the backend pushes updates via `window.evaluate_js(...)`, calling two global functions defined in `web/app.js`: `appendLog(message)` and `onDownloadComplete(status)`, where `status` is `'success' | 'partial' | 'error' | 'cancelled'`. Renaming either JS function requires updating `_log` / `_finish_download` in `main.py`.

**Tools run as modules of the app's own Python** (`PYTHON -m yt_dlp`, `PYTHON -m spotdl`, preferring `python.exe` over `pythonw.exe`), not whatever is on PATH. That way the version `check_environment()` reports and `update_tools()` upgrades is exactly the one used.

**Download flow:**
1. The frontend picks the tool by URL (`spotify` → `'spotdl'`, otherwise `'yt-dlp'`) and sends `options`: `url, folder, mainFormat` (`mp3` = audio, `mp4` = video), `advFormat`, `quality`, `playlist, metadata, subs, sponsorblock`. Options whose checkbox is hidden for the current source are sent as `false`.
2. `_run_download` validates, builds the command with `build_ytdlp_command` / `build_spotdl_command`, and `_stream` runs it, forwarding stdout to `_log` (progress lines throttled to ~10/s) and counting error/success lines.
3. The final status comes from the exit code plus those counts: yt-dlp runs with `--ignore-errors`, so a playlist with some failed items ends as `'partial'`.
4. `updateStatusFromLog` in `app.js` maps known yt-dlp/spotdl lines to a readable status. yt-dlp gives `[download] NN%`. spotdl never prints percentages, so progress is computed from `Found N songs` and the count of `Downloaded`/`Skipping` lines.

**Cancellation / shutdown:** the running `Popen` is stored in `self._process` under `self._lock`; `_busy` guards both downloads and updates. `cancel()` kills the process tree (`taskkill /T` on Windows, so ffmpeg children die too). After `webview.start()` returns, `api.shutdown()` clears the window reference and cancels any running download. Don't call `evaluate_js` while holding `_lock`.

**Updates:** `check_environment()` compares installed versions (`importlib.metadata`) with PyPI's latest and reports whether ffmpeg and deno are present. `update_tools()` runs `pip install --upgrade "yt-dlp[default]" spotdl` in a single command, because spotdl pins `yt-dlp<NEXT_YEAR`. Upgrading yt-dlp alone could break spotdl. When the latest yt-dlp exceeds that pin, it's reported as `blocked`, not outdated. `yt-dlp[default]` matters: it pulls `yt-dlp-ejs` (YouTube JS challenges) and `mutagen` (cover embedding).

**yt-dlp decisions (verified with real downloads + ffprobe — keep them unless re-verified):**
- Video uses `-S` sorting, not `[ext=...]` filters. MP4 prefers `vcodec:h264` because plain "best mp4" picks AV1, which many players can't open. H.264 caps at 1080p on YouTube, so the UI hides 1440p/4K for MP4. MKV/WEBM are the max-quality options.
- Audio M4A/OPUS select the matching source codec (`ba[acodec^=mp4a]`, `ba[acodec=opus]`) and skip `--audio-quality` when quality is "best", so the audio is copied rather than re-encoded. MP3 "best" must pass `--audio-quality 0`, because yt-dlp's default of 5 means ~128 kbps.
- `--embed-thumbnail` fails the whole download for WAV (and isn't supported for WEBM). See `THUMBNAIL_AUDIO` / `THUMBNAIL_VIDEO`. Audio covers are cropped square via `--ppa ThumbnailsConvertor+FFmpeg_o:...`.
- Subtitles: `--sub-langs all` or `en.*` pull dozens of machine translations (`en-de`, …), leave loose `.vtt` files and trigger HTTP 429. `SUB_LANGS` is an anchored es/en list. `--write-auto-subs` is included because most videos only have auto captions.
- `--no-playlist` only matters for `watch?v=…&list=…` URLs; pure playlist URLs always download fully. `OUTPUT_TEMPLATE` puts playlists in a subfolder with numbered files.
- `ARTIST_FROM_TITLE` parses "Artist - Title" only when the video has no artist field (the `§` sentinel trick), so YouTube Music metadata isn't overwritten.

**YouTube account (Premium):** `connect_account(browser)` runs yt-dlp with `--cookies-from-browser` once. It dumps the browser's cookies to a temp file, `_filter_cookies` keeps only youtube.com/google.com entries in `%APPDATA%\MusicDownloader\youtube_cookies.txt`, and the temp file is always deleted. Downloads with `useAccount` pass that file (`--cookies` for yt-dlp, `--cookie-file` for spotdl). Chromium browsers lock their cookie DB while open ("Could not copy Chrome cookie database"), so the browser must be fully closed during import. Chrome and Edge also use app-bound encryption that yt-dlp can't decrypt ("Failed to decrypt with DPAPI"), which is why Vivaldi/Firefox/Brave are listed first. `KNOWN_ERRORS` maps common yt-dlp/spotdl failures to Spanish "Explicación: …" lines, which `app.js` shows under the progress bar.

**Duplicate detection (yt-dlp):** every yt-dlp run appends `extractor\tid\tkind\ttitle\tfinal_path\twebpage_url` to `%APPDATA%\MusicDownloader\history.tsv` via `--print-to-file after_move:…`. Older lines have no url (5 fields); `load_history` accepts both and rebuilds the url for YouTube. The last line for an `(extractor, id)` wins, so a replaced file's new path is the one remembered. In `skip` and `metadata` modes, `_run_download` rebuilds `skip_archive.txt` from history entries of the same kind (audio/video) whose file **still exists**, and passes it as `--download-archive`. That's why a song is skipped even in another folder or format, but downloaded again if the user deleted the file. `_stream` turns yt-dlp's "has already been recorded in the archive" into `Ya lo tienes: <title> → <path>`. yt-dlp also skips on its own a file with the same name in the folder ("has already been downloaded"), but it **still runs the post-processors on it**, so tags and cover get rewritten without downloading the audio. spotdl isn't covered by the history: it only recognizes files in the destination folder named as it would name them (`Skipping …`).

**If I already have it (`options.existing`):** the "Si ya lo tengo" select sends `'skip' | 'replace' | 'metadata'`. Older frontends sent only `skipExisting`, which still maps to `skip` (true) or to no history and no overwrite (false).
- `skip`: the behavior described above.
- `replace`: yt-dlp runs without the archive and with `--force-overwrites` ("Deleting existing file" → `Reemplazando: …`), spotdl with `--overwrite force` ("Overwriting" → `Reemplazando: …`). Only same-name files in the destination folder are overwritten: a copy in another folder is left alone and a new one is downloaded here.
- `metadata` (verified with ffprobe: same audio stream hash, tags and cover restored, also for MP4 video): spotdl uses `--overwrite metadata` ("Updated metadata for …" → `Metadatos actualizados: …`). It only finds files that keep spotdl's name and the chosen format in the folder, and it downloads whatever is missing. A `[revisar]` file is found only on the relaxed retry, if the first pass fails again. yt-dlp has no such mode, so it reuses the post-processor behavior: in the main run, history matches are archived and `_stream` queues them in `_to_retag` instead of reporting them. Then `_retag_known` runs one yt-dlp per file with `-o` pointing at the existing path (`retagPath`, with `%` escaped) and the file's own extension as `advFormat`. Every item gets `metadata=True` forced, and SponsorBlock is turned off because the file is already cut. Same-name files in the folder are reprocessed inline (`EXISTING_LINE` → `Metadatos actualizados`), and missing items are downloaded normally.

**spotdl retry:** songs spotdl can't match (`<spotify url> - LookupError`, printed thanks to `--print-errors`) are retried in a second run with `--dont-filter-results`. The output template adds `REVIEW_TAG` (`[revisar]`) to the filename because the match may be a different recording. An `Aviso: …` line tells the user.

**spotdl notes:** audio only, and it always embeds metadata and downloads whole lists. The UI hides or locks those options for Spotify links, while `state.format` / `state.metadata` keep the user's own choice for other links. `--bitrate disable` skips conversion for m4a/opus and is used for lossless formats. It needs `COLUMNS=200` in the env, or rich wraps its output at 80 columns. It runs with `cwd=folder` because it saves to the working directory. `--dont-filter-results` was removed on purpose, since the filters prevent wrong-song matches.

**Frontend options:** `FORMAT_OPTIONS`, `AUDIO_QUALITY`, `VIDEO_QUALITY` and `MP4_MAX` in `app.js` must match what `main.py` handles. `updateHints()` explains non-obvious trade-offs, for example that FLAC/WAV can't improve lossy YouTube audio. `updateExistingHint()` explains the "Si ya lo tengo" mode for the current source, and shows `replace` as a warning. `metadata` mode locks "Incrustar metadatos" on, like Spotify links do (`metadataLocked()`). The final summary counts `newFiles` (replaced files included), `updated` (`Metadatos actualizados: …`) and `skipped` (`Ya lo tienes: …`) separately.

**Self-update (GitHub releases):** `VERSION` (repo root) is the single source of the app version: `main.py` reads it as `APP_VERSION` and `build_installer.ps1` uses it as the default `-Version`. On startup `app.js` calls `check_app_update()`, which reads `{UPDATE_API}/releases/latest` (no token, 6 s timeout; `MUSIC_DOWNLOADER_UPDATE_URL` overrides the `https://api.github.com/repos/LeandroDoliri/music-downloader` base for local tests) and compares the `vX.Y.Z` tag. No network or a bad response returns `available: false` and nothing is shown. `reason` is `'git'` when `.git` sits next to `main.py` (only a notice, never replace repo files) or `'installer'` when the release has no `MusicDownloader-update-*.zip` asset. `apply_app_update()` holds `_busy`, downloads the zip into `_update\` inside the install, checks GitHub's asset `digest` when present, rejects unsafe zip paths, and `_verify_update` requires the manifest version to match the tag, every file to be listed with a matching sha256, and nothing outside `APP_FILES` (`main.py`, `icon.ico`, `VERSION`, `requirements.txt`, `web/`). If the manifest's `min_runtime` is greater than the install's `RUNTIME` file (missing = 1), nothing is replaced and the release page opens: that release needs the full installer. If `requirements.txt` differs (1.0.0 installs have none), it runs `pip install --no-build-isolation -r` with the app's Python first. `_swap_app_files` moves the old files to `_update\backup` and puts the new ones in place, restoring the backup if any step fails. Files the package doesn't ship are left untouched, because the backup is deleted afterwards. pip can't be rolled back, so if it ran, the error says the dependencies may already be upgraded. Then `_restart()` launches `pythonw.exe main.py` (signed; never a custom `.exe`) detached and destroys the window after 1 s so JS still gets the result. Bump `RUNTIME` by hand when a release needs a different Python, ffmpeg or deno.

**Release flow:** bump `VERSION` (and `RUNTIME` if the runtime changed), run `tools/build_installer.ps1`, then create the GitHub release `vX.Y.Z` with `MusicDownloaderSetup.exe` (the README links `releases/latest/download/MusicDownloaderSetup.exe`, so rename it without the version) and `MusicDownloader-update-X.Y.Z.zip` as assets. 1.0.0 installs predate the updater: those users have to install 1.1.0 by hand once.

**Persistence:** user preferences are stored in the webview's `localStorage` under `music_downloader_*` keys — there is no backend config file. Advanced format/quality are saved per mode (`advFormat_mp3`, `advFormat_mp4`, …), so the main format must be restored and the selects regenerated before applying them. "Si ya lo tengo" is deliberately **not** saved: every launch starts at `skip`, so nobody replaces or retags a whole library by a choice left over from last time.
